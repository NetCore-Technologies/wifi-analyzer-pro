# Scheduled report webhook worker

The local report-job outbox can be delivered by a separate, opt-in worker process. The worker shares the same SQLite report-job store as the API server and claims jobs using the existing expiring leases.

## Start

Run from the repository root:

    python -m wifi_analyzer_backend.report_worker

Configure the process through protected service-manager environment injection or protected secret files:

| Variable | Required | Default | Purpose |
|---|---:|---|---|
| WIFI_ANALYZER_REPORT_WEBHOOK_URL | Yes | — | HTTPS notification endpoint on port 443 |
| WIFI_ANALYZER_REPORT_WEBHOOK_ALLOWED_HOSTS | Yes | — | Comma-separated exact DNS hostname allowlist |
| WIFI_ANALYZER_REPORT_WEBHOOK_KEY_ID | Yes | — | Public signing-key identifier |
| WIFI_ANALYZER_REPORT_WEBHOOK_SIGNING_SECRET or WIFI_ANALYZER_REPORT_WEBHOOK_SIGNING_SECRET_FILE | Yes | — | HMAC-SHA256 secret (32–4096 UTF-8 bytes) |
| WIFI_ANALYZER_REPORT_WORKER_ID | No | Generated | Worker identifier |
| WIFI_ANALYZER_REPORT_WORKER_POLL_SECONDS | No | 5 | Idle polling interval (1–300 seconds) |
| WIFI_ANALYZER_REPORT_WORKER_BATCH_SIZE | No | 1 | Jobs claimed per cycle (1–5) |
| WIFI_ANALYZER_REPORT_WORKER_TIMEOUT_SECONDS | No | 8 | Per-connection timeout (1–30 seconds) |
| WIFI_ANALYZER_REPORT_WORKER_LEASE_SECONDS | No | 120 | Initial and renewed job lease (15–3600 seconds) |
| WIFI_ANALYZER_REPORT_WORKER_EVENT_MODE | No | summary | summary or summary_and_findings |
| WIFI_ANALYZER_REPORT_WORKER_MAX_FINDINGS | No | 100 | Finding events in extended mode (1–499) |

The API must enqueue a due report first. The worker does not create schedules or invent report data; it claims only jobs already present in the durable queue.

## Container sidecar

The Docker image includes the worker and runs as an unprivileged UID. Start the API container normally, then start a second container using the same image, the same persistent volumes and the protected worker configuration. For example, after naming the API container wifi-analyzer-pro:

    docker run --rm --volumes-from wifi-analyzer-pro \
      --env-file /secure/path/report-worker.env \
      --entrypoint python wifi-analyzer-pro:local report_worker.py

The API and worker must share the same HOME configuration and XDG state volumes so they use the same local account files and SQLite report-job queue. Restrict the environment file to the service account, or use your orchestrator's secret facility. The worker has no listening port.

## Delivery and security guarantees

- The endpoint must be HTTPS on port 443 and its hostname must match an exact allowlist entry. IP literals, embedded credentials, URL queries and fragments are rejected.
- DNS is resolved immediately before delivery. Every returned address must be globally routable; one private, loopback, link-local, reserved or scoped answer blocks the entire resolution set.
- The TCP socket connects directly to the exact resolved IP. TLS uses the original DNS hostname for SNI and certificate hostname verification, requires a trusted certificate and TLS 1.2 or 1.3, and does not use HTTP_PROXY or HTTPS_PROXY.
- Only the validated socket sends the signed request. Redirects are never followed. Only 2xx responses complete a job.
- Request and response sizes are bounded. Response bodies are discarded after a 16 KiB limit; raw response content and transport exception text are not persisted.
- HMAC-SHA256 signatures and stable job idempotency keys are generated by the existing report-delivery package. A retry reuses the same key so the receiving system can deduplicate a delivery accepted before a worker crash or lease expiry.
- A worker lease is renewed immediately before transmission. Completion and failure updates are accepted only while the same lease is still active.
- Signing material is never included in a report bundle or job result. The signing-secret file option requires a regular file no larger than 4096 bytes and, on POSIX systems, no group or other permissions. Prefer a service-manager credential facility; do not place secrets in source control, command-line arguments or ordinary world-readable environment files.

This scheduled-report worker supports one configured report notification destination per process. For multi-subscription router-event webhook delivery, use the separate durable dispatcher described in WEBHOOK_DISPATCH_WORKER.md. Production rollout still requires customer-managed secret provisioning and rotation, per-tenant access controls, delivery dashboards, operational alerting and an independently reviewed deployment boundary.

## Operational notes

A lost worker can leave a job leased until the lease expires; the next claim cycle recovers it through the queue's bounded retry policy. A notification receiver should honor the Idempotency-Key header because a network timeout can occur after the receiver has committed the request but before the worker records completion. A retry is not proof that the receiver did not process the first attempt.
